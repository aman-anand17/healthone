# DECISIONS.md — settled design decisions

Every entry here was debated and closed in design sessions before this repo
existed. Reopen one only with a reason; record the change here if you do.

## Product

| # | Decision | Rationale |
|---|---|---|
| P1 | Product = Patient Safety Case Investigator inside a Patient & Member 360 | One coherent workflow beats feature soup; directly satisfies the challenge |
| P2 | Primary user = Clinical Case Reviewer (Priya). Patient is the subject, never the user | Challenge rejects patient-facing chatbots; keeps scope safe |
| P3 | Fictional org = HealthOne Group, a payvider (hospital network + health plan) | Legitimizes holding provider AND payer data about one person |
| P4 | Hero scenario: CardioZen (invented drug) + chronic kidney disease + serum potassium, 90-day monitoring | Concrete and clinically believable; invented drug ⇒ no real guidance misquoted |
| P5 | Reviewer starts from a review QUEUE, never a random patient | Makes it an application, not a search box |
| P6 | Queue always contains one case the reviewer should DISMISS (test recorded under a variant name) | Proves detection is imperfect and the human is load-bearing, not decorative |
| P7 | Workflow closes with a stored disposition: Escalate / Request additional evidence / Mark reviewed / Dismiss with reason | Closed loop; audit trail; the system never orders clinical tests |
| P8 | Governing principle: AI proposes → human approves → deterministic checks apply → human decides | The whole safety story; repeat it in the demo |

## Rules & extraction

| # | Decision | Rationale |
|---|---|---|
| R1 | Extraction runs AT INGEST into a proposal queue; a human approves before a rule activates. Never live-extraction-as-dependency in the demo | Demo determinism + genuine governance; live demo beat = approving a fresh doc, which is staged and rehearsed |
| R2 | Rule schema: drug, precondition_type (condition/age_min/none), precondition_value, required_test, interval_days, interval_source_phrase (verbatim), effective_date, source_doc, source_passage, needs_review, review_reason | Verbatim phrase = honesty check; passage = citation |
| R3 | Interval normalization is LITERAL: quarterly=90, every 3 months=90, N weeks=N×7, N months=N×30. **12 weeks = 84, never 90.** Policy is written down; approval screen shows raw phrase → normalized value | Silently rounding a number in a safety rule is indefensible; caught as a team error, now a demo talking point |
| R4 | Controlled vocabulary reference table for drugs/conditions/tests; extraction must map into it | Prevents free-text drift; makes joins deterministic |
| R5 | Rules are versioned and immutable. Corrections = new version; retirement flips status; cases store rule_id + version | Edge case 8.6; wrong-rule-approved has a recovery path |
| R6 | Overlapping rules for same drug+condition+test: approver supersedes or consciously keeps both; stricter interval governs detection; both cited | Edge case 8.8 |
| R7 | A document may contain NO rule; extraction returning nothing is correct behavior. Test corpus includes one distractor document | Edge case 8.5; restraint is a feature |
| R8 | LLM = Snowflake Cortex AI_COMPLETE with a Claude model, called from SQL, inside the account. Verify entitlement first; record GA fallback | Keeps the "no data leaves" story intact; Claude-in-Cortex ≠ external API |

## Case detection & evidence

| # | Decision | Rationale |
|---|---|---|
| C1 | Case detection is DETERMINISTIC SQL (a dynamic table joining active rules to 360 timelines). No LLM decides whether a case exists | Testable, auditable; AI never adjudicates |
| C2 | Trigger: drug active AND precondition met AND no qualifying test result within interval (+ grace) | The core check |
| C3 | Monitoring window anchored to later of (drug start, condition onset, rule effective date) | Edge case 8.3: a lab predating the drug must not count |
| C4 | Grace window (interval + 7 days, recorded on the rule) before a gap case opens | Edge case 8.2: boundary flip-flop suppression |
| C5 | Evidence verdicts: **exactly three — AGREES / CONFLICTS / MISSING.** CHANGED-OVER-TIME cut from v1 (rule versioning stays; period-effective temporal evaluation does not) | Fourth verdict = temporal rule resolution inside a dynamic table = a week of work for one demo line |
| C6 | Conflict TYPES are engineered (e.g., EHR ACTIVE + no pharmacy fill in window); instances are data-driven | Fires on unscripted patients too; AI explains verdicts, never produces them |
| C7 | Negative evidence wording, verbatim pattern: "No <test> result was found in the available records between <start> and <end>." A MISSING claim always carries a `searched` field | Claims about our data, never about reality; absence becomes evidence, not silence |
| C8 | Priority is rule-based with visible factors; no scores, no ML | Challenge forbids opaque predictions |

## Architecture

| # | Decision | Rationale |
|---|---|---|
| A1 | Everything in ONE Snowflake account: data, documents, rules, cases, audit, app | The governance pitch: no data leaves |
| A2 | UI = Streamlit in Snowflake, WAREHOUSE runtime | Container runtime rejected: Cortex Agents API needs it, too risky in 12 days |
| A3 | NO Cortex Agent on the critical path. Assistant = Cortex Search (docs) + AI_COMPLETE (explanation) orchestrated explicitly in Python | SiS warehouse runtime can't call Agents API; explicit orchestration = auditable tool selection (sell it, don't apologize) |
| A4 | Case detection = dynamic table. Demo uses a "Refresh queue" button running ALTER DYNAMIC TABLE … REFRESH; intermediates use TARGET_LAG = DOWNSTREAM | Min lag 60s + chained compounding = dead air on stage without the button |
| A5 | No stored procedures / external functions inside dynamic table definitions (platform constraint). Reconciler runs as a separate step over detected cases | Snowflake limitation, designed around |
| A6 | Cited answer in the demo is TEMPLATE-GENERATED from reconciler output; free-text Q&A is an enhancement layered on top | Demo must not depend on the first thing on the cut list |
| A7 | Identity crosswalk = one deterministic mapping table (patient_id ↔ member_id → person_id), stated plainly as the seat a production MPI would fill | Honest, isolated, replaceable; no fake unmatched-records theatre |
| A8 | Table names may echo FHIR resource names where natural; NO FHIR conformance layer is built | Conformance costs days, buys one sentence |
| A9 | Follow-up questions route to a fixed set of evidence-retrieval functions + semantic view, not free generated SQL | Reliability + scores the custom-tools criterion |

- **2026-08-31 (C31) — There IS a numeric score on proposals, and it is a
  measurement rather than an opinion.** Reverses the narrower reading of C29.
  A model's self-reported confidence stays banned: uncalibrated, and a decimal
  beside a drug-safety rule invents precision nobody measured. But the share of
  deterministic document checks that passed is a real quantity, so
  `V_PROPOSAL_CORROBORATION.CORROBORATION_SCORE` publishes it, labelled
  "document checks passed" and never "AI confidence".
- **2026-08-31 (C32) — The two gate checks carry 10; everything else 4/2/1.**
  Equal-ish weights let a proposal whose quoted phrase was absent from the
  document score 85%. Failing the fabrication detector must not read as a pass,
  so section-exists and phrase-verbatim dominate the arithmetic. The UI colours
  the number by the BAND, not by its own value, so an UNCORROBORATED proposal
  can never render green.
- **2026-08-31 (C33) — Every score must be decomposable on the card.**
  `CHECKLIST` lists all nine checks with verdict and weight on every proposal,
  including the ones that passed quietly, and a test asserts the ticked weights
  recompute the displayed percentage exactly. An undecomposable score is either
  over-trusted or ignored.
